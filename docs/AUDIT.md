# AuthFlow — Architecture & Production-Readiness Audit

A senior-level review of the codebase as it stood after the full spec was
implemented (through commit `bd9e8df`): file/directory structure, system
design, performance, memory/resource handling, dependency hygiene, and test
coverage — followed by fixes for everything that was a genuine bug or a
material production-readiness gap. Four commits came out of this,
`1cb9ecb` → `db38433`. This document is the write-up: what was found, what
was actually fixed (with evidence, not just claims), and what's deliberately
left as a documented recommendation rather than implemented.

## How this was done

Read every file under `backend/app` and `backend/tests` fresh (33 app
files, 16 test files), cross-checked every declared dependency against
actual usage via grep, and looked closely at the concurrency-sensitive
paths (password hashing, DB session handling, JWT issuance/validation)
since that's where async-framework bugs like to hide. Findings that looked
real were verified two ways before being called "fixed": the automated
suite, and a live run against the actual Neon database — not just the
isolated test DB.

## Fixed

### 1. Password hashing was blocking the entire event loop (performance, `1cb9ecb`)

`get_password_hash`/`verify_password` were plain synchronous functions
doing Argon2 work — deliberately expensive by design, that's what makes it
resistant to brute-forcing — called directly from `async def` service
functions (register, login, both profile-update paths, admin create).
Calling blocking CPU-bound code inline in an async function blocks
FastAPI's single-threaded event loop for the call's entire duration,
which stalls *every other in-flight request on that worker*, not just the
one doing the hashing.

Measured with a throwaway benchmark before fixing it: 5 concurrent
password hashes delayed an unrelated concurrent coroutine (standing in for
something like a `/health` check or another user's login) by **428ms
worst-case**. After wrapping the calls in `asyncio.to_thread`: **22ms** —
roughly a 20x reduction, and the gap widens further under real concurrent
auth traffic, since the blocking version serializes completely.

Fix: both functions are now `async`, running the actual Argon2 call via
`asyncio.to_thread`. All 5 call sites and the unit tests updated to await
them.

### 2. Password changes didn't invalidate existing JWTs (security, `037714e`)

A JWT only ever encoded `sub` (user id) and `exp`. `get_current_user`
re-checked role and soft-delete status from the DB on every request (a
deliberate design choice from earlier in the build), but never checked
whether the password had changed since the token was issued. A stolen
token stayed fully valid for its entire remaining lifetime even after the
legitimate user "secured" their account by changing the password.

Fix: added a `token_version` column, bumped on every password change
(self-service and admin-forced alike). `create_access_token` now embeds it
as a `ver` claim (plus `iat`, which was also missing); `get_current_user`
rejects any token whose version doesn't match the user's current one.

Live-verified against Neon: registered a user, logged in, confirmed the
token worked, changed the password, confirmed the *same, still-unexpired*
token was immediately rejected with 401, and a fresh login worked. Also
confirmed a *non*-password update does **not** invalidate the token —
only password changes do.

Same migration also added an index on `users.type`, since `GET /users`
filters by it and a full table scan gets real at scale. The
autogenerated migration originally added `token_version` as `NOT NULL`
with no default, which would fail against any table that already has
rows — fixed by hand with `server_default='1'` before applying it.

### 3. Inconsistent/leaky error handling, silent health check, unbounded pool (`a71d43a`)

Three related gaps, all under "will this survive contact with production":

- **No catch-all exception handler.** A genuine bug (as opposed to one of
  our own `AppError` subclasses) fell through to Starlette's default
  handler, which returns **plain text**, not JSON — every other error
  response in the app is `{"detail": "..."}`. Added a handler for the base
  `Exception` class; FastAPI/Starlette still route `AppError`/
  `HTTPException`/`RequestValidationError` to their own more specific
  handlers first (confirmed this doesn't shadow them), so this only
  catches genuinely unexpected exceptions. Logs the real traceback
  server-side, returns the generic shape to the client — no internals
  leaked.

- **`/health` was a hardcoded `{"status": "ok"}`,** unconditionally. A
  completely unreachable database would still report healthy to whatever
  is routing traffic based on that endpoint. Now does a real `SELECT 1` —
  through the same `get_db` dependency every other route uses, not the
  `engine` object directly, so it still respects the test-DB override
  instead of needing live Neon connectivity during test runs (this was a
  real mistake in the first draft of this fix, caught before committing).

- **Connection pool size/overflow/recycle were hardcoded** to whatever
  SQLAlchemy defaults to, with no way to tune them per environment. Now
  configurable via `DB_POOL_SIZE`/`DB_MAX_OVERFLOW`/`DB_POOL_RECYCLE_SECONDS`
  (Postgres only — SQLite, the zero-config local fallback never used in
  production, uses a different pool class that doesn't accept these kwargs
  at all, so it's conditional on the same `get_backend_name()` check
  already used for the SSL config).

- **`SECRET_KEY` defaulted to `"change-me"`** with nothing stopping that
  from reaching a real deployment — the classic footgun where an
  `.env.example` gets copied as-is. `Settings` now refuses to start if
  `ENVIRONMENT != "development"` and `SECRET_KEY` is still the default.

- Added a `lifespan` handler that calls `engine.dispose()` on shutdown, so
  pooled connections close cleanly instead of being dropped by process
  exit — mainly matters for graceful restarts (reload, container
  recycling).

### 4. Dead code, unused dependencies, and a coverage-measurement bug (`db38433`)

- Removed three dead stub files (`crud/base.py`, `schemas/common.py`,
  `db/init_db.py`) — all leftovers from the original scaffold's guesses at
  patterns (a generic `CRUDBase`, a generic `PagedResponse[T]`) that never
  got used because the concrete, per-feature implementations turned out to
  be simpler and clearer for a single-model app.
- Removed `python-multipart` (declared for `Form()`/`OAuth2PasswordRequestForm`-style
  parsing that was never adopted — login is JSON) and `faker` (declared,
  never imported in any test) from the dependency manifests. Also removed
  the `REFRESH_TOKEN_EXPIRE_MINUTES` setting — no refresh-token feature was
  ever built, so it was dead configuration.
- `pytest-cov` was installed but never actually invoked anywhere. Wired it
  up properly (coverage config in `pyproject.toml`, documented command in
  the README) rather than leaving it dormant.
- Doing that surfaced a genuine, separate bug: **coverage.py's default
  settings silently under-report everything that runs after an
  `await db.execute(...)`-style call**, because SQLAlchemy's async engine
  bridges to sync DB-API calls via `greenlet` switches internally, and
  coverage.py's line tracer doesn't follow those switches unless told to.
  Before the fix, `app/api/deps.py` measured 69% — with the `token_version`
  check and the soft-delete check both showing as "uncovered" *despite
  dedicated tests exercising exactly those branches*. Fixed with
  `concurrency = ["greenlet", "thread"]`. After the fix: `deps.py` is
  genuinely 100%, and the true project-wide number is **96%**, not the
  ~86% the unfixed config was reporting. The corrected numbers also
  exposed one real, still-open gap, which got a new test: a token for a
  user id that no longer exists at all (distinct from soft-deleted, which
  finds a row and was already covered).

## Current state

- **95 tests passing**, 96% line coverage (measured correctly — see above).
- Full live verification re-run against the real Neon database after all
  four fixes landed together, in one pass: register → login → get profile
  → non-password update (token still valid) → password change (old token
  now rejected) → public stats — all correct. Test data cleaned up
  afterward, `users` table empty.
- Zero known unused dependencies, zero known dead files.

## Recommended, not implemented

Everything below is a legitimate next step for a system that needs to
handle real production traffic and real attackers — but each one is a new
subsystem, not a fix to something that exists, and none were asked for.
Listed here so the gap is a documented decision, not an oversight:

- **Rate limiting / brute-force protection on `/auth/login`.** Right now
  nothing stops unlimited password guesses against a known email. Generic
  error messages prevent *enumeration*, but not *guessing*. Needs a
  rate-limit store (Redis, or an in-process limiter if single-instance)
  and a decision on limits/lockout policy.
- **Trigram (`pg_trgm`) indexes for the `ILIKE '%...%'` filters** on
  `city`/`first_name`/`last_name`/`email`. The plain btree index just added
  on `type` genuinely helps that exact-match filter; it does **not** help
  the partial-match ones — a leading-wildcard `LIKE` can't use a standard
  btree index at all. At current/expected scale this doesn't matter yet;
  it will if the user table grows into the hundreds of thousands and
  `GET /users?city=...` stays a common query. Fixing it properly means
  `CREATE EXTENSION pg_trgm` plus GIN indexes, which is a real
  infrastructure decision, not a code change I'd make silently.
- **Structured/observability logging** — request IDs, correlation IDs
  tying a log line back to a specific request across the DB and
  application layers. Right now logging is just SQLAlchemy's own engine
  echo plus uvicorn's access log plus the new catch-all handler's
  `logger.exception`.
- **Refresh token rotation.** Access tokens are 30 minutes with no refresh
  flow — a deliberate scope boundary from earlier in the build, not
  something this pass changed. Still the right thing to flag for a system
  that wants longer-lived sessions without re-prompting for a password
  every 30 minutes.
- **Security headers middleware** (HSTS, `X-Content-Type-Options`, etc.) —
  standard hardening, cheap to add, just genuinely out of scope for this
  pass.
- **CI actually running `ruff`/`black`/`mypy`/`pytest`.** All four are
  configured in `pyproject.toml` and work when invoked by hand, but
  nothing runs them automatically on push/PR yet.
- **Containerization** (Dockerfile, docker-compose for local Postgres) —
  not attempted; the project currently assumes a hosted Postgres (Neon)
  and a local venv.
